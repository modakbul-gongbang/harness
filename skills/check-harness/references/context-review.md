# 컨텍스트 구조 리뷰

목적은 더 많은 파일을 만들게 하는 것이 아니라 필요한 지침을 적절한 범위에서 찾게 하는 것이다.
길이와 파일 개수는 관찰값이며 합격선이 아니다.
현재 구조가 합리적이면 유지할 이유도 적는다.

## 1. 문서 인벤토리

적용되는 상위·루트 CLAUDE.md, 프로젝트 내부의 하위 CLAUDE.md, `.claude/rules/**/*.md`와 연결된 가이드를 수집한다.
생성물, build, vendor, node_modules, 다른 프로젝트, 비밀 파일과 개인 자동 메모리는 제외한다.
심볼릭 링크는 실제 경로로 중복 제거하고 순환 참조를 따라가지 않는다.
명시적으로 링크된 외부 가이드는 범위와 접근 가능 여부를 확인하며 임의로 홈 디렉토리를 확장 탐색하지 않는다.
접근 불가·제외 경로는 미확인 범위에 남긴다.

각 파일에 상대경로, 역할, 전체 줄 수, 문자 수, 큰 섹션의 줄 범위, 적용 범위, 로딩 방식을 기록한다.
측정하지 않은 값은 미측정으로 표시하며 문자 수를 토큰 수로 단정하지 않는다.
단일 파일이라는 이유로 참조 단계가 0이라고 추정하지 않는다.
변경 후 참조 단계나 줄 수는 재측정 전까지 예상으로 표시하며, 제안한 방법이 유일한 해법이라고 단정하지 않는다.

| 파일 | 역할 | 줄 수 / 문자 수 | 적용 범위 | 로딩 방식 |
|---|---|---|---|---|
| 실제 조사 경로 | 공통/영역/절차/참조 | 실제 측정값 | 프로젝트 전체 또는 경로 | 상시/경로 조건/명시적 읽기/미확인 |

`@import`는 부모와 함께 로딩되고 파일 분할만으로 비용이 줄지 않는다.
하위 CLAUDE.md와 Rules의 `paths`를 실제로 읽어 적용 범위를 확인한다.
단순히 '백엔드에서만'이라는 문장이 있다고 조건부 로딩으로 분류하지 않는다.
현재 cwd 기준 상시 로딩 후보와 영역별 조건부 파일을 따로 합산하고 중복 경로는 한 번만 센다.
런타임 로딩 증거가 없으면 '설정 기반 추정'이라고 표시하며 실제 로딩량·토큰 사용량으로 부르지 않는다.

## 2. 구조별 관찰과 권장안

| 관점 | 확인할 것 | 개선을 권할 근거 |
|---|---|---|
| 길이·밀도 | 긴 파일/섹션에 서로 다른 책임이 섞였는가 | 길이만이 아니라 특정 작업에서 불필요한 내용과 그 위치 |
| 책임 분리 | 루트에는 공통 안내, 하위에는 영역 맥락이 있는가 | 특정 영역의 긴 상세 지침이 모든 작업에 읽히는 사례 |
| 중복 | 같은 규칙·명령을 여러 곳에서 관리하는가 | 양쪽 파일:라인, 의도적 요약/링크인지 구분 |
| 충돌 | 동일 작업에 서로 다른 지시를 주는가 | 양쪽 인용과 적용 범위; 의도 불명확하면 확인 질문 |
| 발견 가능성 | 가이드 진입점·링크·읽는 조건이 명확한가 | 깨진 링크, 고립 문서, 실제로 따라간 참조 경로 |
| 과도한 분할 | 짧은 파일들이 같은 책임을 나눠 갖는가 | 한 작업을 이해하는 데 필요했던 참조 단계와 통합 후보 |
| 조건부 적용 | Rules paths와 하위 위치가 대상 코드와 맞는가 | 실제 대상 파일 예시, 잘못 매칭하거나 누락하는 범위 |
| 유지보수 | 코드·명령과 문서가 일치하는가 | 현재 코드/명령과 다른 문서의 위치 |

200줄은 긴 파일을 다시 살펴보는 참고 신호로만 사용할 수 있다.
200줄 초과 자체로 FAIL, 자동 분할 또는 일정 줄 수로 축소를 요구하지 않는다.
짧은 파일의 충돌도 놓치지 않고, 긴 파일이라도 일관된 공통 지침이면 유지 의견이 가능하다.
분리 권장에는 이동할 섹션, 후보 경로, 읽는 시점, 줄어드는 중복/불필요한 로딩과 추가 탐색 부담을 적는다.
기존 하위 CLAUDE.md나 가이드가 적합하면 새 Rules 파일보다 재사용을 먼저 검토한다.
실제 결함과 선택적인 구조 개선을 구분하고 취향을 팀의 필수 정책으로 바꾸지 않는다.

## 3. 결과 형식과 말투

컨텍스트 결과는 '현재 구조 → 잘 된 점 → 확인할 점 → 권장 개선' 순서다.
근거가 없으면 칭찬이나 개선안을 억지로 만들지 않는다.
권장안마다 관찰 사실, 영향, 선택 가능한 최소 변경, 유지해도 되는 조건을 제시한다.

- 권장 예: '루트의 API 규칙은 백엔드 작업에만 쓰입니다. 기존 backend 가이드로 옮기고 읽는 조건을 남기면 상시 지침을 줄이는 데 도움이 됩니다. 모든 작업에 필요한 규칙이라면 현재 위치를 유지해도 됩니다.'
- 피할 예: '300줄이므로 FAIL입니다. 반드시 Rules 3개로 나누세요.'
- 확인된 실패 예: 'Hook 명령이 가리키는 파일이 없어 실행할 수 없습니다. 실제 파일 위치에 맞춰 경로를 수정하는 것을 권장합니다.'

부드러운 말투를 위해 실제 실행 실패나 깨진 경로를 숨기지는 않는다.
